# domain_mix 回归诊断 — 数据修复(M2/M2b/M5)致 monet/synth 被挤没

**日期**: 2026-06-26 · **代码基线**: `mot_pilot_v1_cleanup`(branch `cleanup-merge`, 工作区未 commit 的数据修复) · **作者**: Claude(接手数据线任务, 受 Evan 委托)

> 本文是 **plan-only 诊断**(不改代码), 给 Evan 评审后再定修复方向。
> 触发: 上一个 agent 实现审计 §8 的 M2/M2b/M5(并发取图 + anime 强制行级分片)后, 今天 12:55 跑的 16-rank 验证 probe(`probe_mix16_datafix`) **FAIL, 且 mix 比修复前更差**。该 probe 很可能在 OOM kill 之后才出结果, 上个 agent 没看到。

---

## 0. 一句话结论

数据修复 **把 per-rank 漂移(M2b/M5)修好了**(anime per-rank σ 5.8%→0.8%, 每 rank 拿全 17 shard), **但把聚合 domain_mix 搞崩了**: monet_real 39.7%→**0.6%**、synthetic 5%→**0.1%**。根因是 **并发取图(fetch_workers=8)+ anime 行级 17 shard 让 anime/gpic 产出暴涨, 资源(网络/挂载/CPU)被它们的取图线程过订阅 → 走 tar 流式、未提速的 monet/synth producer 被饿到几乎不产出 → buffer 空 → sampler 按 present 域 renorm 把份额全摊给 anime/gpic**。

**结论: 这套数据修复目前不能作为 stage256 重跑 / 512 的基础, 必须先解决"快域挤掉慢域"。** 修复方向有 4 个候选(§4), 需 Evan 拍板, 且要用 **多-rank GPU 短跑 + 新的 `mix_*` 埋点**复验(0-GPU probe 会高估严重度, §3)。

## 2. 机制: 为什么慢域会被"挤没"(逐行核实)

数据线是 **每域 1 个 producer 线程 → 各自 bounded queue → 各自 shuffle buffer(deque) → sampler 带放回抽样**。三个环节叠加导致回归:

### 2.1 致命设计: buffer 每批"无差别"排空 bs//2(与 mix 目标无关)
[complete_dataset.py:568-572](../training/dataline/complete_dataset.py#L568-L572):
```python
# 滚动 buffer：淘汰最旧 bs 个（deque maxlen 也会自然淘汰），下轮补新
for d in self.domains:
    for _ in range(min(bs // 2, len(buffers[d]))):
        buffers[d].popleft()
```
**每个 batch, 对【每一个域】无条件 popleft `bs//2` 个**(bs96 → 每域每批扔 48)。补料则靠 [complete_dataset.py:445-449](../training/dataline/complete_dataset.py#L445-L449) 的非阻塞 `get_nowait` 从该域 queue 拉。

→ 一个域要保持"present", **它的 producer 必须每个 batch-间隔补 ≥ bs//2**。**这把"域是否 present"完全绑定到 producer 吞吐, 与 domain_mix 目标无关**: domain_mix 只决定 sample_one 抽哪个 buffer, 不影响这个均匀排空速率。慢域(monet/synth)只要产出 < bs//2/批就被抽干 → 空 → 消失。

### 2.2 sampler 对 absent 域 renorm-away(放大器, 非根因)
[sampler.py:137-138](../training/dataline/sampler.py#L137) + [config.py:103-108](../training/dataline/config.py#L103-L108):
```python
present = {d for d, p in pools.items() if p.n > 0}   # buffer 空 → 不 present
dm = cfg.domain_mix_renorm(stage, present)            # 只保留 present、重归一到 1.0
```
monet/synth buffer 空 → 不 present → 它们的 39.7%/5% 份额被 **renorm 全摊给 anime/gpic** → anime 30→57%、gpic 25→42%。**这本是"某域临时断供"的安全兜底, 现在因 producer 严重失衡变成了常态。**

### 2.3 根因: 修复只加速了 anime/gpic, 还过订阅资源饿死了 tar 域
数据修复做了两件事(都只作用于 anime/gpic, **没碰 monet/synth 的 tar 流式**):
- **并发取图** `_prefetch_raw`(fetch_workers=8): anime 逐 URL HTTP、gpic 逐文件随机读各开 8 线程池。
- **anime 强制行级分片**(force_row_level): 每 rank 读全 17 anime shard(原来 1~2), 数据池 + 产出双涨。

后果(资源过订阅):
- 每进程: anime(8 fetch 线程)+ gpic(8 fetch 线程)= **16 并发取图线程**; 每节点 8 进程 → **~128 并发 GET**(R2 + mountpoint-s3) + 32 个 producer 主线程做 decode。
- monet/synth 走 `stream_tar_images` 顺序流(单线程, 没加并发), 在这种 **网络带宽 / mountpoint-s3 连接池 / GIL+CPU** 的过订阅下被挤到几乎不产出(probe 实测 ~0 img/s)。
- 上个 agent 已部分意识到("decode 进池让 anime 过供刷屏 → 已回退串行 decode", 见 `_prefetch_raw` docstring), 但 **只回退了 decode、保留了 fetch 并发**, 不够 —— fetch 并发 + 行级 17 shard 仍让 anime/gpic 过快。

> **注**: 我尚未隔离出"过订阅"的具体瓶颈是 网络带宽 / 挂载连接数 / 还是 GIL+CPU。三者都可能, 但机制("加速快域 → 过订阅 → 饿死慢 tar 域")明确。隔离实验见 §3。

## 3. 重要校准: 0-GPU probe 会**高估**严重度

probe 是 0 GPU, loader 全速空转(无模型 forward 节流), 这会 **过度压榨慢 producer**, 比真实训练严重:
- **0-GPU**: 每秒做很多 batch → §2.1 的 `bs//2/批` 排空速率极高 → 慢域瞬间被抽干。
- **真实 GPU 训练**: 每 step ~2.5–3s 被 forward 节流(`smk_p1_datafix` 单卡实测 iter 2.9s、data_wait_frac 落到 ~5%, **不 data-bound**) → 排空速率低得多 → 慢 producer 有时间回填。

但 probe 显示 monet **producer 速率本身 ≈ 0**(不是"产出 50/s 但被抽走"), 说明 **§2.3 的绝对 producer 饥饿是主因, 在 GPU 训练里同样存在**(网络/挂载/CPU 过订阅与 GPU 节流无关); §2.1 的排空放大是 probe 特有, GPU 下会缓解。

**推论**:
1. 回归是**真问题**(producer 饥饿), 不是纯 probe 假象 —— 不能直接拿去开 512。
2. 但 **monet 0.6% 这个具体数字被 probe 放大了**; 真实 16-rank GPU 训练里 monet 可能不至于到 0.6%, 量级未知。
3. **必须用多-rank GPU 短跑复验真实 mix**(单卡 smoke 看不出: 单 rank 无 16 路争抢、anime 也不被行级放大)。好在 M1 已落地 `mix_*` 埋点(写 metrics.jsonl) → 直接读真值, 不用再事后离线 probe。

### 隔离实验(确认根因 + 找瓶颈, 0 GPU 即可, 便宜)
| 实验 | 控制变量 | 看什么 |
|---|---|---|
| A | `fetch_workers=1`(退串行) vs 8 | 并发取图是不是过订阅元凶 |
| B | anime force_row_level 关 vs 开(fetch_workers 固定) | 行级 17 shard 的产出放大贡献 |
| C | 只跑 monet producer(无 anime/gpic 争抢) 测其纯吞吐 | monet tar 在无争抢下能产多少(对比 §2.1 需求) |
| D | 同 A/B/C 但 **GPU 1×8/2×8 短跑读 `mix_*`** | 真实训练的 realized mix(权威判据) |

## 4. 修复方向(4 候选, 需 Evan 拍板)

核心病根 = **§2.1 的"均匀排空"把 mix 绑死在 producer 吞吐上**。围绕它有 4 条路, 可组合:

| # | 方向 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|---|
| **F1** | **排空 ∝ 消费**(改 §2.1) | 不再每域无脑 pop bs//2, 而是 **按本批各域实际被抽中的数量 pop**(或按 domain_mix 比例) | 直击根因: 4% 的域只掉 ~4%bs, 慢 producer 也跟得上; 与 mix 目标自洽 | 改 buffer 语义, 要保持 rolling/shuffle 性质 + 写测试 |
| **F2** | **sampler 不轻易 renorm-away 目标域**(改 §2.2) | 目标域 absent 时 **阻塞补料等它**(带超时回退), 而非直接重归一 | mix 锁定到目标; 训练 compute-bound(data_frac<0.04)等得起 | 某域真死会 stall → 必须有超时兜底(已有 first_fill_timeout 机制可复用) |
| **F3** | **取图并发改保守 / 限域 / 限节点**(改 §2.3) | fetch_workers 调小、或**只给 gpic**(真·逐文件瓶颈)、anime 仅靠 M3(403不重试)+ /local 缓存; 或按"每节点总并发"限流 | 直接消除过订阅、不动 buffer 逻辑 | 治标不治本: "合适并发"依赖节点/网络, 要扫参; gpic 提速幅度可能缩水 |
| **F4** | **给 monet/synth 也提速 / 各域 buffer 保底** | tar 域也加并发预取; 或维持每域 buffer 下限(低于阈值就阻塞补) | 让所有域吞吐对齐 | tar 顺序流并发化复杂; buffer 保底只是缓解、不解根因 |

**我的初步倾向(待你拍)**: **F1(排空∝消费) 为主 + F3(并发改保守, 至少 anime 别行级×8) 兜底**。理由:
- F1 是唯一从"绑死在吞吐"解耦的根治法, 且让 sampler 的 renorm 回归"罕见兜底"本意。
- F3 顺手消掉过订阅(也对 §6 TextAtlas 这个新的挂载流式域有利)。
- F2 单独用会牺牲吞吐且依赖超时, 作为 F1 之上的可选加固。
- **每一步都用 §3 实验 A–D + `mix_*` 埋点复验**, 改一项验一项(坑点#11: 别边跑边改)。

**未定/需你决定**:
1. 选哪条(组合)修复路径?
2. 修复后用什么口径判"合格"? (聚合 ±5% + per-rank 极差上限? 用 0-GPU probe 还是 2×8 GPU `mix_*`?)
3. anime 行级分片是否保留(它修好了 M5/M2b, 但放大了产出)—— 倾向保留 force_row_level、把"过快"交给 F1/F3 解决, 而非退回文件级(否则 per-rank 偏斜回来)。
