# T2 H100 GPU 踩坑与集群使用建议

> 本文源自 T2 向量过滤作业（FAISS/cuVS），非 MOT 训练；§后续使用集群建议 的通用建议(资源申请/Pending诊断/OOM排查)对任何 H100 作业适用，FAISS/cuVS 部分仅过滤相关。
>
> ⚠️[待核实 2026-06-27: T2_H100 是否属 MOT 文档范围]

更新时间：2026-06-14

## 一句话结论

最开始不是 H100 不能用，也不是集群 GPU 整体坏了；T1 已经证明 PyTorch CUDA 可以正常使用 H100。真正的问题是 T2 旧路线依赖 `faiss-gpu`，当前 wheel 在 H100/sm90 上缺可用 kernel，运行时会报：

```text
CUDA error 209 no kernel image is available for execution on the device
```

所以早期只能先退回 CPU 路线。后续验证发现 NVIDIA cuVS 的 IVF-Flat 在 H100 上可用，因此 T2 GPU 路线已经从 FAISS GPU 改成 cuVS。

## 当时踩到的坑

1. PyTorch 能用 GPU，不等于所有 GPU 库都能用。

   T1 走 PyTorch CUDA，所以 H100 可以正常跑；T2 旧实现走 FAISS GPU，失败点在 FAISS wheel 对 H100/sm90 的支持，而不是 GPU 本身。

2. FAISS GPU 失败方式比较硬。

   报错发生在底层 CUDA/C++，可能直接 abort 进程，不一定能被 Python 正常捕获。因此不能把全量任务直接压上去试，必须先做很小的 stack probe。

3. 8 卡任务第一次 Pending 的主因是 CPU 申请过大。

   集群单节点大约是：

   ```text
   GPU: 8
   CPU: 95.69 core
   Memory: 1.93 TB
   ```

   旧 8 卡 YAML 申请：

   ```yaml
   gpuPerWorker: 8
   cpuPerWorker: 160
   memGBPerWorker: 1200
   ```

   `160 CPU` 超过单节点总量，所以调度器无法把这个 job 放到任何一台机器上。内存 `1200GB` 虽然偏大，但不是这次 Pending 的第一原因。

4. 日志少不代表没跑。

   JCC 外层日志只显示 pod 启动和 shell 输出；真正进度由 Python 脚本打印。全量任务还可以通过数 S3 输出 shard 来判断是否推进。

5. 不能混用不同 backend/参数的中间输出。

   CPU FAISS、GPU FAISS、cuVS 的输出目录必须分开。全量正式输出只允许同一套 backend 和参数断点续跑，否则会混入不同召回特性的结果。

6. 大产物必须写 S3。

   本项目大产物统一写：

   ```bash
   /s3-pixai-test-uw2/evan/mot_filtering_v1
   ```

   不要把全量结果写到 FSX，也不要写到别人的 S3 目录。

## 已验证的事实

已完成验证：

1. T1 4 卡 PyTorch CUDA 路线成功，产出 100,000,000 行 GPIC pass。
2. T2 CPU IVFFlat tiny/medium 成功，说明 S3 输入、S3 输出、MONET manifest、GPIC pass 都是可用的。
3. T2 GPU stack probe 中，PyTorch CUDA 成功，FAISS GPU 在 H100 上失败。
4. T2 cuVS stack probe 成功。
5. T2 cuVS 1 卡 medium 成功，命中数与 CPU medium 接近，并且明显更快。

- cuVS IVF-Flat Python API：https://docs.rapids.ai/api/cuvs/stable/python_api/neighbors_ivf_flat/

## 后续使用集群的建议

1. 新 GPU 任务先跑 stack probe。

   至少验证：

   ```bash
   nvidia-smi
   python -c 'import torch; print(torch.cuda.is_available())'
   ```

   如果依赖 FAISS、cuVS、xformers、flash-attn 等底层库，还要各自做最小 GPU 样例，不要只看 PyTorch。

2. H100 上的向量检索优先用 cuVS。

   当前不要再提交旧 FAISS GPU 路线，除非后续有人重新编译并验证过支持 sm90 的 FAISS GPU 包。

3. JCC 资源申请要能放进单节点。

   对单 worker 的 8 卡任务，`gpuPerWorker: 8` 通常意味着整台节点都要给这个 pod，因此 CPU 不能超过单节点约 `95.69 core`。建议先用：

   ```yaml
   gpuPerWorker: 8
   cpuPerWorker: 64
   memGBPerWorker: 700
   ```

   如果 CPU 确实成为瓶颈，再逐步提高到 80 或 90，不要一上来写 160。

4. 全量任务前必须有 medium pilot。

   pilot 要检查三件事：

   - job 是否 Succeeded；
   - `summary.json` 是否存在；
   - 命中数量是否与 CPU 或旧版本结果在合理范围内。

5. 输出目录按任务类型隔离。

   例如：

   ```bash
   t2_sscd_ivfflat_cpu_medium
   t2_sscd_cuvs_1gpu_medium
   t2_sscd_cuvs_gpic_monet_hits
   ```

   full 正式任务只复用同 backend、同阈值、同 `nlist/nprobe` 的输出目录。

6. Pending 时优先检查资源申请。

   如果 job 长时间 Pending，先看：

   - `gpuPerWorker` 是否要求整机；
   - `cpuPerWorker` 是否超过单节点总量；
   - `memGBPerWorker` 是否把可用节点排除了；
   - 是否还有旧 job 占着同一批 GPU。

7. OOMKilled 时先降并发和内存峰值，不要盲目重跑。

   本项目 S3/parquet 读取容易制造 page cache 和内存峰值。遇到 OOM 时优先：

   - 减小 batch；
   - 降低 worker 数；
   - 避免一次性缓存过多 DataFrame；
   - 明确把大中间结果写 S3；
   - 用独立输出目录重试或确认断点续跑参数完全一致。
